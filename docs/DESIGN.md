## 1. 系统是什么

给蓝领的灵活用工平台。一句话概括主链路:

```
工厂发岗 → 工人报名 → 录用(占名额) → 签电子协议 → 履约完成
        → 结算算钱 → 资金域代发 → 佣金/报表/通知
```

技术形态是 **Spring Modulith 模块化单体**:一个进程、20 个业务域,
每个域独占 PostgreSQL schema 与独立 DataSource、独立最小权限数据库用户。
不是微服务,但域之间的隔离强度接近微服务——这是刻意的:
上一代系统 12 个模块共用一个库、195 个服务塞在一起,改一处炸一片。

## 3. 三个贯穿全局的机制

### 3.1 跨域事件:outbox + 中继

所有跨域事件都经 outbox。发布方把事件行与业务数据**同事务落库**,
各域的中继(`@Scheduled`)取出、投递、按结果标记。

```
业务方法(事务) ──写业务数据 + 写 outbox 行── 提交
                                              │
中继(事务) ──lockPendingBatch(SKIP LOCKED)──> publishEvent ──> 各消费方(@EventListener,REQUIRES_NEW)
                        │                          │
                        └── 全成功 → PUBLISHED     └── 有失败 → FAILED + 指数退避,留在表里等重试
```

关键取舍(细节与守卫见 ARCHITECTURE-RULES 铁律 4):

- **为什么每个域一张 outbox 表而不是共享一张**:每个域有独立 DataSource,
  共享表意味着业务写和事件写落在两个事务里,"同事务落库"这个前提就没了。
  约束本身指向唯一答案。
- **为什么消费方是 `@EventListener` 而不是 AFTER_COMMIT**:后者要等中继事务提交后才跑,
  那时行已被标 PUBLISHED,消费方再抛异常事件就永久丢了。
- **为什么要退避**:不退避的话一个坏掉的下游会被以中继频率反复捶打;
  更要命的是取批按 id 升序且有上限,足够多的坏事件会把批次头部占满,后面的永远排不上。
- **为什么必须幂等,且用业务键**:投递是至少一次。eventId 只是某次投递的编号,
  换一个就绕过去了;定义"这单算过工资"的是履约单。

运维面:`OutboxAdmin` 汇总各域卡死事件(重试超阈值的),`/api/ops/outbox` 提供查看与人工重放,
需要 `PLATFORM_OPS` 角色。超阈值的日志从 WARN 升为 ERROR ——WARN 会被日常噪音淹没,
而资金链路上"这条事件发不出去"意味着有人的钱没到账。

### 3.2 授权:两层,都要过

| 层 | 问的问题 | 实现 |
|---|---|---|
| 归属校验 | "你是不是这个资源的主人?" | 各域自己判断,依赖本域的只读副本 |
| 平台角色(RBAC) | "你有没有做这类事的权限?" | `identity.user_role`,每次现查 |

**归属校验不能被角色替代**:"这个人是不是这个组织的法人代表"依赖具体资源。
反过来,组织审核、放款、结算作废、佣金支付这几个动作的"主人"是平台自己,
没有归属可查,只能靠角色。

角色不写进 JWT,理由见铁律 5。`PLATFORM_ADMIN` 管角色、`PLATFORM_OPS` 干活,
两者分开:运维不能自己升权;管理员要动钱得先显式给自己授运维角色——**那会留下痕迹**。

### 3.3 钱:资金域是唯一动钱者

任何域要动钱都调 `FundApi`,不自己记账扣余额(§4.1 决策#1)。
`spendFromAccount` 强制要求幂等键:调用方与资金域是两个事务,
钱出去之后调用方回滚,不带键就会重复扣款,且流水里认不出哪笔是重复的。

代发是**三段式**:

```
①事务内:预扣监管账户 + 落 PENDING 代发单   ← 乐观锁在这一段就校验完
②事务外:调支付通道                          ← 外部 IO 不占数据库事务与账户行锁
③事务内:记结果(成功/失败原路退回)
```

原来三段挤在一个事务里,而 `@Version` 要到提交时才校验:两笔并发时双方都读到同一版本、
**两笔钱都真的打出去了**,然后其中一笔撞乐观锁全部回滚——系统认为"什么都没发生"。

## 4. 主链路上的关键不变式

| 不变式 | 由什么保证 |
|---|---|
| 同一人对同一岗位只能报一次名 | `UNIQUE (job_id, applicant_user_id)`。**缺了它下游 5 个唯一约束全部失效**,因为每次 applicationId 都不同 |
| 名额不会超发 | 名额扣减闭环在岗位域;占满即关闭是同一个操作;CHECK 约束兜底 |
| 录用失败不烧名额 | 状态守卫在跨域扣名额**之前**执行 |
| 一笔结算只生成一张工资单 | `settlement.application_id UNIQUE` + 消费方按业务键幂等 |
| 一笔工资只发一次 | `payout.settlement_id UNIQUE` + 代发单 `idempotency_key UNIQUE` |
| 已发放的结算不能被静默作废 | `Payout.cancel()` 对 PAID 抛错,要求走冲正 |
| 协议签署是履约完成的前置门禁 | engagement 持有已签协议的只读副本 |

## 5. 已知的缺口

诚实记录,不粉饰。详细分析见 `../AUDIT-2026-07-27.md`。

**尚未实现**
- 保险集成(用户指示暂缓,有现成模式可循)
- 岗位关闭之外的其它生命周期动作(下架后重新上架)
- 报表的 `DIRECT_COST` 从未被写入,平台盈亏被系统性高估
- 商城资金链路未接 `FundApi`:报表上有收入,账本上没有一分钱
- 语音撤回不真的关闭岗位;语音采集到的名额被丢弃(固定按 1 个建岗)
- 微工卡的"代征代缴"是空壳,无预扣税计算

**已知弱点**
- 无 actuator / 健康检查 / 指标。11 个中继的积压量、20 个连接池的水位都不可观测
- 日志密度低:337 个源文件里只有 4 个有 logger,资金代发全链路零日志
- 连接池 `maximumPoolSize(3)` 是为测试调小的值,**单实例 60 连接,两实例即超 PostgreSQL 默认上限**——水平扩容目前堵死且没写在任何部署文档里
- 测试零隔离:全靠手工分配 ID 号段避免撞车,没有机制保护这套约定
- `CreditBasedDepositPolicy` 是全库唯一一处金额参与 `double` 运算(该方法目前无生产调用方)
