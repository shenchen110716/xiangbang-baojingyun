# 架构铁律

> 这份文件只写**真的被机器守住**的规则,以及每条由哪个测试守。
> 它之前写着"CI 强制,不靠自觉",而两个守卫当时都名不副实:
> schema 隔离只验了 20 个域里的 1 个,Modulith 因为没有域声明依赖白名单而**对生产代码恒绿**。
> 一条没人执行的规则比没有规则更糟——它让人以为已经安全了。

## 铁律 1:独立 schema,最小权限,禁止跨域读表

每个域独占一个 PostgreSQL schema,并使用只授权本域的数据库用户。跨域读写被数据库以
`permission denied` 拒绝,而不是靠代码自觉。

**守卫**:`SchemaIsolationTests` —— 41 条用例。对 20 个域**逐个**验证:
①连接用的是 `<域>_user` 且不是超级用户;②读其它 19 个域的表都会被拒。
外加一条"域清单必须覆盖所有已配置数据源",防的是新增域时忘了加进清单、于是静默漏测。

## 铁律 2:跨域只走 `api` 包与领域事件

`<域>/internal` 对外不可见。跨域交互只能引用 `<域>/api` 下的接口与事件记录。

**守卫**:`ModularityTests`(Spring Modulith `verify()`)。
每个域的 `package-info.java` 都声明了 `allowedDependencies` 白名单——
**没列在里面的域一旦被引用就失败**。这是它从"恒绿摆设"变成真守卫的关键:
在此之前 22 个 package-info 一个都没声明,依赖边全部不受约束。

依赖图以各 `package-info.java` 为准,这份文档不重复一遍——重复的东西迟早对不上。

## 铁律 3:数据自持,不查他域的库

需要他域数据时订阅其领域事件,在本域维护只读副本。铁律 1 会在数据库层挡住违规,
但设计上就该自觉:副本是有意为之的冗余,不是妥协。

例:`profile.posted_job_ref`(岗位属于哪个组织)、`review.approved_org`(谁是法人代表)、
`engagement.posted_job`。正因为有这些副本,"改岗位画像要校验归属"这类判断才不必跨域查库。

## 铁律 4:跨域事件必须经 outbox 投递

事件行与业务数据**在同一个事务里**落库,再由中继投递。丢事件在这个系统里不是"少条通知",
而是"工资单永远不生成""佣金永远不入账"——这些后果**不会自愈**,因为不会有第二次事件。

- **outbox 表必须在发布方自己的 schema 里。** 每个域有独立 DataSource,
  放共享 schema 就变成跨事务,一个成功一个失败,保证直接作废。守卫:`OutboxContractTests`
- **消费方必须用 `@EventListener`,不能用 `@TransactionalEventListener(AFTER_COMMIT)`。**
  中继在自己的事务里 publish;AFTER_COMMIT 的监听器要等中继事务提交后才跑,
  那时 outbox 行已被标成 PUBLISHED,它再抛异常事件就永久丢了。守卫:`OutboxContractTests`
- **调度入口不得自调用事务方法。** `relayScheduled()` 里直接写 `publishPending();`
  会绕过 Spring 代理、`@Transactional` 静默失效——SKIP LOCKED 的行锁立刻释放、
  多实例重复投递、批内各自提交。必须经 `ObjectProvider<自身>` 调用。
  守卫:`OutboxSchedulingContractTest`
- **一个消费方失败不连累其他消费方。** 默认广播器是同线程顺序调用,中间一个抛异常
  其后的永不执行。`OutboxEventMulticasterConfig` 接住每个监听器的异常并继续,
  中继取走这批异常后整条重试。
- **投递语义是至少一次,消费方必须幂等。** 幂等键要用**业务键**(履约单、结算单),
  不是 eventId——eventId 只是某一次投递的编号,换一个就绕过去了。
- 注意:主键手工赋值的实体,Spring Data 的 `save()` 走 `merge()`,那是 upsert,
  **不会撞主键**。用"先查后插 + save"给这类实体做去重在并发下是无效的,
  要用 `INSERT ... ON CONFLICT DO NOTHING` 让数据库裁决。

## 铁律 4.5:被多方写入的投影必须有乐观锁

只读投影常常被多个事件源写入(例:`worker_projection` 的标签来自画像域、
信用分来自评价域)。每个监听器都是"读整行 → 改一个字段 → 整行写回",
且各自 `REQUIRES_NEW`——没有 `@Version` 时,后提交的一方**把先提交的改动整个盖掉**,
不报错也不留痕。

冲突方失败后由 outbox 中继重投、基于新数据重放,这正是重试机制存在的意义。

**守卫**:`ProjectionConcurrencyTest`。它一写出来就抓到了第二处同样的缺陷。

## 铁律 5:授权由身份域裁决,且不写进 JWT

平台级角色存在 `identity.user_role`,每次判断都向身份域查。
不放进 token 是因为:token 里的声明只有等过期才失效,而这些角色能做的是
**重放资金事件**,收回权限必须立刻生效。代价是每次高权限请求多一次索引查询。

RBAC 是**粗粒度的一层**,不替代归属校验。"这个人是不是这个组织的法人代表"
依赖具体资源,粗粒度角色表达不了,两者都要过。

## 铁律 6:凭据与外部通道不许有"能跑就行"的默认值

- 所有凭据占位符**不带默认值**。漏配环境变量时应用启动失败,
  而不是悄悄用仓库里公开的那个字符串当密钥。
- 三个外部通道(代发/电子签/推送)的 mock 实现由 `xbb.channel.mode` 显式控制。
  它们**静默成功**:代发会扣减监管账户、把发放标 SUCCESS、写入假的完税凭证号、
  通知工人"工资已发放",而钱一分没出去——错误被系统自己确认为成功并层层扩散。
  这种东西绝不能靠"上线前记得换实现"。

## 为什么是这些规则

上一代系统 12 个模块共用一个库、195 个服务塞在一起,改一处炸一片。
这几条是 v1.0 与它的根本分野。

但最值钱的一条经验来自 2026-07-27 的审计:**规则要靠机器守,而"守卫存在"不等于"守卫有效"**。
写下规则、写一个同名的测试、然后假设它在起作用——这个链条断在最后一环,断了还不会有任何症状。

所以加规则时顺手问一句:**如果我现在违反这条规则,哪个测试会红?**
答不上来,就说明它还没被守住。同理,写完测试问一句:**它测的路径和生产跑的路径是同一条吗?**
——11 个 outbox 中继的事务失效了很久没人发现,就是因为测试调的是代理 bean,
而生产跑的是调度器,两条不同的路。

还有一条,来自查那个"约三次挂一次"的间歇性失败:**症状可疑时先测量,别先解释。**
我先后按"测试隔离"和"事件乱序"两个说得通的故事改了两轮代码
(两轮都修到了真缺陷,但都不是这个 flake 的成因),直到插日志拿到失败现场的数据,
才在十分钟内定位到真因是投影的丢失更新。看代码推理出的故事很容易自洽,
而自洽不等于正确。
